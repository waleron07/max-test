# Чат MAX на GREEN-API

Веб-интерфейс для отправки и получения текстовых сообщений в мессенджере **MAX** через [GREEN-API](https://green-api.com/max).

## Что реализовано

- подключение к инстансу GREEN-API по `idInstance` / `apiTokenInstance` с проверкой состояния через `GetStateInstance`;
- ввод номера как в MAX: выбор страны с флагом и телефонным кодом, форматирование национальной части по маске;
- проверка номера получателя через `CheckAccount` перед открытием чата: если аккаунта в MAX нет, чат не открывается, а пользователь видит понятное сообщение;
- канонический числовой `chatId` берётся из ответа `CheckAccount`, имя контакта для шапки — из `GetContactInfo`;
- отправка текстовых сообщений методом `SendMessage` с мгновенным показом сообщения;
- статусы исходящих как в MAX: часы — в пути, ✓ — отправлено, ✓✓ — доставлено, цветные ✓✓ — прочитано (вебхук `outgoingMessageStatus`, а для истории — поле `statusMessage`);
- получение входящих и исходящих сообщений через HTTP API (`ReceiveNotification` → обработка → `DeleteNotification`);
- список чатов аккаунта (`GetChats`) со счётчиком непрочитанных и превью последнего сообщения, отсортированный по свежести переписки;
- история переписки при открытии чата (`GetChatHistory`);
- входящее сообщение от собеседника, которого ещё нет в списке, создаёт чат само — ни одно текстовое сообщение не теряется;
- отбор уведомлений: обрабатываются только текстовые сообщения нужного чата, остальные типы пропускаются, но корректно удаляются из очереди;
- предупреждение, если у инстанса задан `webhookUrl` или отключены уведомления о входящих — в этом случае очередь HTTP API остаётся пустой;
- обработка ошибок сети и API с понятными сообщениями, нарастающая пауза при сбоях опроса;
- интерфейс в духе MAX: пузыри входящих и исходящих, время сообщения, автопрокрутка, пустое состояние, состояния загрузки и блокировки, светлая и тёмная темы, адаптивная вёрстка;
- Enter — отправка, Shift+Enter — перенос строки, пустые сообщения не отправляются.

## Использование

Проверить можно двумя способами:

- **онлайн** — [waleron07.github.io/max-test](https://waleron07.github.io/max-test/) (публикуется на GitHub Pages автоматически при пуше в `main`);
- **локально** — склонировать репозиторий и выполнить `npm install` и `npm run dev`, см. раздел «Запуск».

Дальше в обоих случаях одинаково:

1. Откройте приложение.
2. Введите `idInstance` из личного кабинета GREEN-API.
3. Введите `apiTokenInstance`.
4. Нажмите «Подключиться» — приложение проверит, что инстанс авторизован.
5. Выберите страну и введите номер получателя, затем нажмите «Открыть».
6. Напишите сообщение и отправьте его (Enter).
7. Ответ получателя из MAX появится в чате автоматически.

> Хост API определяется автоматически: сначала пробуется выделенный сервер инстанса
> (`https://7107.api.greenapi.com` для `idInstance`, начинающегося на `7107`), затем универсальный
> `https://api.green-api.com`. Поля `apiUrl` в интерфейсе нет — задание требует от пользователя только
> `idInstance` и `apiTokenInstance`. Нестандартный адрес можно задать переменной `VITE_GREEN_API_URL`
> (шаблон — в `.env.example`).

> Важно: чтобы приём сообщений работал через HTTP API, у инстанса должен быть **пустой `webhookUrl`** и включённые уведомления
> (`incomingWebhook`, `outgoingWebhook`) — это настраивается в личном кабинете или методом `SetSettings`.

## Архитектурные решения

**Сортировка и превью чатов.** `GetChats` не отдаёт времени последней переписки, поэтому сразу после подключения запрашиваются журналы `LastIncomingMessages` и `LastOutgoingMessages` за 30 дней: из них строятся превью и порядок списка — свежие чаты сверху. Это два запроса на подключение вместо истории по каждому чату отдельно.

**Список чатов и история.** При подключении загружается `GetChats` (личные чаты; группы и каналы заданием не предусмотрены), при открытии чата — `GetChatHistory` на 50 сообщений, один раз на чат: дальше список пополняют уведомления. Сообщения хранятся как `Record<chatId, Message[]>`, дубли схлопываются по `idMessage`, поэтому история и уведомления могут приходить в любом порядке.

**Хост инстанса.** У GREEN-API часть инстансов живёт на выделенных серверах, и на универсальном хосте такие инстансы отвечают не на все методы: авторизация проходит, а очередь уведомлений и журналы оказываются пустыми. Поэтому при подключении перебираются кандидаты — `https://<первые 4 цифры idInstance>.api.greenapi.com`, затем `https://api.green-api.com` — и дальше используется тот, который ответил.

**Слои.** `src/api` — единственное место, где приложение знает об HTTP и адресах GREEN-API; `src/types` — типы API и внутренняя модель `Message`; `src/utils` — чистые функции (номера, разбор уведомлений); `src/hooks` — опрос очереди; `src/components` — интерфейс. В разметке нет ни одного вызова `fetch`.

**Хранение состояния.** Состояния немного (учётные данные, открытый чат, список сообщений, признаки загрузки и ошибки), живёт оно в одном `App`, поэтому хватает `useState` и передачи свойств. Redux, Zustand или React Query добавили бы зависимость и лишний слой без выигрыша.

**Клиент API.** `createGreenApiClient({ idInstance, apiTokenInstance, apiUrl })` возвращает объект с методами `getStateInstance`, `sendMessage`, `receiveNotification`, `deleteNotification`. Клиент пересоздаётся через `useMemo` только при смене учётных данных — это же служит ключом перезапуска опроса.

**Опрос очереди.** Хук `useReceiveNotifications` запускает ровно один последовательный цикл на клиента:
`receiveNotification` (длинный опрос, `receiveTimeout=20`) → передача уведомления в обработчик → `deleteNotification(receiptId)` → следующий запрос. Цикл живёт в `useEffect` с зависимостью от клиента и отменяется через `AbortController` при размонтировании и смене учётных данных, поэтому параллельных циклов не возникает. Пустая очередь приходит либо пустым телом, либо статусом `408` по истечении `receiveTimeout` — и то и другое означает «сообщений нет» и просто начинает новую итерацию (с минимальным интервалом в секунду, чтобы не получить плотный цикл, если сервер закроет ожидание сразу). При сетевой ошибке пауза растёт от 1 до 30 секунд, чтобы не бить запросами без остановки. Обработчик уведомлений хранится в `ref`, так что его пересоздание на отрисовке не перезапускает цикл.

**Проверка номера и определение чата.** Валидация идёт в два уровня. В форме номер вводится по маске страны, и кнопка «Открыть» неактивна, пока он не набран полностью. Затем вызывается `CheckAccount`: он отвечает, есть ли такой аккаунт в MAX, и возвращает канонический числовой `chatId` вида `10000000` — по нему входящие уведомления совпадают точно. Если аккаунта нет, чат не открывается. `CheckAccount` поддерживает только номера России и Беларуси, поэтому для остальных стран проверка пропускается и используется `79991234567@c.us`; сбой самой проверки тоже не блокирует открытие чата — номер мог быть верным. Имя контакта для шапки подгружается отдельно через `GetContactInfo` и не задерживает интерфейс.

**Обработка уведомлений.** `toMessage` принимает только `incomingMessageReceived`, `outgoingMessageReceived`, `outgoingAPIMessageReceived` с `messageData.typeMessage === 'textMessage'` и достаёт текст из `messageData.textMessageData.textMessage`. Всё остальное (`outgoingMessageStatus`, `stateInstanceChanged`, `quotaExceeded`, вложения) пропускается, но уведомление всё равно удаляется из очереди. `belongsToChat` сравнивает уведомление с открытым чатом по `chatId` (в том числе уточнённому) и, для входящих, по номеру отправителя. Повторы исходящих (показанное сразу сообщение и уведомление `outgoingAPIMessageReceived`) схлопываются по `idMessage` независимо от того, что пришло раньше — ответ `SendMessage` или уведомление. Ответ на отправку, пришедший после закрытия или смены чата, отбрасывается, чтобы не подмешать сообщение в чужую переписку.

## Безопасность

- Учётные данные вводит пользователь; в репозитории их нет, файл `.env` с секретами не попадает в коммиты (в `.env.example` лежит только необязательный адрес хоста).
- `idInstance` и `apiTokenInstance` хранятся в `sessionStorage`: перезагрузка страницы не сбрасывает подключение, но при закрытии вкладки данные исчезают и на диске ничего не остаётся. `localStorage` сознательно не используется — он переживает закрытие браузера и оставляет токен на чужом компьютере. Если сохранённые данные больше не подходят (инстанс разлогинен, токен сменился), они стираются автоматически, а «Отключиться» очищает их сразу.
- Запросы идут напрямую из браузера в GREEN-API, как предполагает задание. В боевом решении токен не должен попадать в код клиента: запросы стоит проводить через собственный сервер (BFF или прокси), который хранит секреты у себя и отдаёт браузеру только данные чата.

## Ограничения

- Список чатов загружается один раз за сеанс; история чата — при первом открытии, дальше её можно перечитать кнопкой ⟳ в шапке. В остальном актуальность поддерживают уведомления.
- Групповые чаты и каналы в списке не показываются: задание ограничено перепиской с пользователем по номеру телефона.
- Поддерживаются только текстовые сообщения — вложения, реакции и статусы доставки не отображаются.
- Если открыть приложение с одними и теми же учётными данными в двух вкладках, они будут разбирать одну очередь уведомлений и часть сообщений увидит только одна из вкладок. Это свойство очереди GREEN-API, а не приложения.
- Решение проверено сборкой, типами, линтером и модульными тестами; полный сценарий отправки и получения требует реального инстанса MAX в GREEN-API.
