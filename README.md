# GREEN-API MAX Chat

Веб-интерфейс для отправки и получения текстовых сообщений в мессенджере **MAX** через [GREEN-API](https://green-api.com/max).

## Что реализовано

- подключение к инстансу GREEN-API по `idInstance` / `apiTokenInstance` с проверкой состояния через `GetStateInstance`;
- открытие чата по номеру телефона получателя (`chatId` формируется как `79991234567@c.us`);
- отправка текстовых сообщений методом `SendMessage` с оптимистичным отображением и статусом отправки;
- получение входящих и исходящих сообщений через HTTP API (`ReceiveNotification` → обработка → `DeleteNotification`);
- фильтрация уведомлений: обрабатываются только текстовые сообщения нужного чата, остальные типы игнорируются, но корректно удаляются из очереди;
- обработка ошибок сети и API с понятными сообщениями, backoff при сбоях polling;
- UI в духе MAX: пузыри входящих/исходящих, время сообщения, auto-scroll, empty state, loading/disabled состояния, светлая и тёмная темы, адаптивная вёрстка;
- Enter — отправка, Shift+Enter — перенос строки, пустые сообщения не отправляются.

## Использование

1. Откройте приложение.
2. Введите `idInstance` из личного кабинета GREEN-API.
3. Введите `apiTokenInstance`.
4. При необходимости поправьте `apiUrl` (адрес хоста API указан в кабинете рядом с инстансом).
5. Нажмите «Подключиться» — приложение проверит, что инстанс авторизован.
6. Введите номер получателя в международном формате, например `79991234567`, и нажмите «Открыть».
7. Напишите сообщение и отправьте его (Enter).
8. Ответ получателя из MAX появится в чате автоматически.

> Важно: чтобы приём сообщений работал через HTTP API, у инстанса должен быть **пустой `webhookUrl`** и включённые уведомления
> (`incomingWebhook`, `outgoingWebhook`) — это настраивается в личном кабинете или методом `SetSettings`.

## Архитектурные решения

**Слои.** `src/api` — единственное место, где приложение знает об HTTP и URL GREEN-API; `src/types` — типы API и внутренняя модель `Message`; `src/utils` — чистые функции (номера, разбор уведомлений); `src/hooks` — polling; `src/components` — UI. В JSX нет ни одного `fetch`.

**State management.** Состояния немного (учётные данные, открытый чат, список сообщений, флаги загрузки и ошибки), живёт оно в одном `App`, поэтому `useState` + пропсы достаточно. Redux/Zustand/React Query добавили бы зависимость и слой абстракции без выигрыша.

**API-клиент.** `createGreenApiClient({ idInstance, apiTokenInstance, apiUrl })` возвращает объект с методами `getStateInstance`, `sendMessage`, `receiveNotification`, `deleteNotification`. Клиент пересоздаётся через `useMemo` только при смене учётных данных — это же служит ключом перезапуска polling.

**Polling.** Хук `useReceiveNotifications` запускает ровно один последовательный цикл на клиента:
`receiveNotification` (long polling, `receiveTimeout=20`) → передача уведомления в обработчик → `deleteNotification(receiptId)` → следующий запрос. Цикл живёт в `useEffect` с зависимостью от клиента, отменяется `AbortController` при unmount и смене учётных данных, поэтому параллельных циклов не возникает. Пустой ответ (пустая очередь) просто начинает новую итерацию. При сетевой ошибке — экспоненциальный backoff от 1 до 30 секунд, чтобы не устраивать tight loop. Колбэк обработки уведомлений хранится в ref, так что его пересоздание на рендере не перезапускает цикл.

**Обработка уведомлений.** `toMessage` принимает только `incomingMessageReceived`, `outgoingMessageReceived`, `outgoingAPIMessageReceived` с `messageData.typeMessage === 'textMessage'` и достаёт текст из `messageData.textMessageData.textMessage`. Всё остальное (`outgoingMessageStatus`, `stateInstanceChanged`, `quotaExceeded`, медиа) отбрасывается, но уведомление всё равно удаляется из очереди. `belongsToChat` учитывает особенность MAX: в исходящий запрос уходит `79991234567@c.us`, а в уведомлении приходит числовой `chatId`, поэтому входящие дополнительно сопоставляются по `senderData.senderPhoneNumber`. Дубли исходящих (оптимистичное сообщение + уведомление `outgoingAPIMessageReceived`) схлопываются по `idMessage`.

## Security

- Учётные данные вводит пользователь; в репозитории их нет и `.env` с секретами не коммитится.
- `idInstance` / `apiTokenInstance` хранятся только в runtime-состоянии React: при перезагрузке вкладки их нужно ввести заново. `localStorage` сознательно не используется — токен инстанса даёт полный доступ к аккаунту, а хранение его в браузере делает уязвимым к XSS; удобство не стоит такого риска в демо-приложении.
- Запросы идут напрямую из браузера в GREEN-API, как предполагает задание. В production токен не должен попадать в клиентский код: запросы стоит проксировать через backend/BFF, который хранит секреты на сервере и отдаёт фронтенду только данные чата.

## Ограничения

- Один открытый чат за раз, без списка чатов и без истории: история сообщений в приложении накапливается только с момента открытия чата (методы получения истории заданием не предусмотрены).
- Уведомления, пришедшие когда чат не открыт или относящиеся к другому чату, удаляются из очереди без отображения.
- Поддерживаются только текстовые сообщения — медиа, реакции и статусы доставки не отображаются.
- Если открыть приложение с одними и теми же учётными данными в двух вкладках, они будут разбирать одну очередь уведомлений — часть сообщений увидит только одна из вкладок. Это свойство очереди GREEN-API, а не приложения.
- Решение проверено сборкой, типами, линтером и unit-тестами; сквозной сценарий отправки/получения требует реального инстанса MAX в GREEN-API.
